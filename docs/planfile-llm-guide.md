# Planfile — LLM-Agnostic Ticket Workflow

> **Goal:** every ticket produced in c2004 must be actionable by *any*
> coding agent — Windsurf, Cursor, Claude Code, SLLM shell clients, GitHub Copilot
> Workspace, or a raw chat session with GPT-4 / Gemini / Qwen3 — without
> further priming. This document explains how we achieve that and how
> to author tickets that any LLM can pick up and close.

---

## Why LLM-agnostic tickets matter

When an alert fires in c2004, `healing-webhook` creates a planfile
ticket. That ticket becomes the **universal hand-off document** between
monitoring and whatever coding agent happens to be attached. If the
ticket is vague ("fix bug") the agent guesses; if it's over-specific
("apply this diff") it defeats the point. The sweet spot is a
**self-contained task package** with:

1. Context — *what* failed, *where*, *when*, *which SHA*.
2. Reproduction — copy-pasteable commands that demonstrate the failure.
3. Acceptance criteria — machine-checkable success conditions.
4. Constraints — guardrails to keep the agent out of trouble.
5. Prompt — a pre-written instruction the agent can quote verbatim.

That is exactly the structure generated by
`monitoring/healing-webhook/ticket_builder.py::LLM_READY_TEMPLATE`.

---

## The universal ticket schema

Every ticket we create carries the following sections in its
`description` field (markdown). **Do not reorder, do not rename** —
agents rely on the H2 headers to find each block.

```markdown
## 🚨 Context
## 🔁 Reproduction
## 📂 Likely-affected areas
## ✅ Acceptance criteria
## 🔒 Constraints
## 🤖 Prompt (LLM-agnostic — copy/paste verbatim)
## 📎 Raw alert payload
```

Plus the standard planfile fields: `id`, `status`, `priority`, `sprint`,
`source`, `labels`. The label `llm-ready` signals to any downstream
tooling that the description adheres to this schema.

## How each agent should consume a ticket

### Windsurf / Cascade
```
/planfile PLF-123
```
or paste:
```
Read @planfile.yaml and pick up ticket PLF-123.
Follow the "🤖 Prompt" section verbatim.
```
Cascade will open the affected files listed in "📂 Likely-affected
areas", reproduce using "🔁 Reproduction", and validate with the
acceptance block.

### Cursor
Open Cursor's chat and paste:
```
@planfile.yaml

Work ticket PLF-123. Use the ticket's own prompt block, then run
`task monitor:probe` to verify.
```
Cursor's `@filename` syntax pulls the whole planfile.yaml into context;
the agent jumps to the ticket by ID.

### Shell clients via SLLM
```bash
planfile ticket show PLF-123 > /tmp/task.md
koru sllm drive --client claude-code --prompt-file /tmp/task.md --execute
koru sllm drive --client aider --prompt-file /tmp/task.md --execute
```

### Raw chat LLM (GPT / Gemini / DeepSeek)
```bash
task planfile:export PLF-123 > prompt.md
# paste prompt.md into any chat window
```

## Tips for writing LLM-agnostic tickets

### 1. Prefer commands over prose

Bad:

> The health endpoint is slow, should probably look at the database pool.

Good:

> Reproduction:
> ```bash
> time curl http://localhost:8101/api/v3/health
> # observed: 4.8s ; expected: <200ms
> ```

### 2. Point at files, not concepts

Bad:

> Fix the menu system.

Good:

> Likely-affected areas:
> - `backend/api/routes/v3/menu.py`
> - `connect-menu-editor/backend/query_handler.py`

A well-scoped path list halves the agent's exploration time.

### 3. Make acceptance machine-checkable

Good acceptance criteria read like assertions:

- [x] `curl -fsS http://localhost:8101/api/v3/schema/version` returns 200
- [x] `pytest backend/api/tests/test_schema.py` passes
- [x] `redsl gate check` exits 0

Avoid fuzzy criteria ("should look cleaner", "works better").

### 4. List constraints explicitly

LLMs will happily refactor 400 lines when you need a 4-line change.
Guard with constraints:

```
## 🔒 Constraints
- Do NOT rename public APIs.
- Keep the diff under 80 lines.
- Must add a regression test.
```

### 5. Use the label taxonomy

Always set:

- `llm-ready` — this ticket follows the universal schema.
- `severity:critical|error|warning` — matches the firing alert.
- `component:backend|frontend|firmware|infrastructure|endpoint`.
- `source:<tool>` — so you can filter
  `planfile ticket list --source alertmanager`.

### 6. Prefer one root cause per ticket

If an alert implicates multiple modules, split the ticket. Small tickets
→ small diffs → green tests.

### 7. Teach the agent how to verify

Every ticket should end with a **one-line verification command** the
agent can run after patching. For c2004 that is usually:

```bash
task monitor:probe
```

which re-runs the realtime-health TestQL scenario.

## Lifecycle

```
  Alert fires ─────────► healing-webhook
                             │
                             ▼
                   ticket_builder.build_ticket_payload(alert)
                             │
                             ▼
                  planfile ticket create [--label llm-ready]
                             │
                             ▼
     planfile.yaml   ←──── sync ────►   TODO.md / GitHub / Jira
                             │
                             ▼
              Developer or LLM opens ticket, fixes code, opens PR
                             │
                             ▼
                   planfile ticket done <ID>
                             │
                             ▼
              CI re-runs probe → if green, alert auto-resolves
```

## Taskfile shortcuts

```bash
task planfile:list              # tickets created from alerts (label: llm-ready)
task planfile:show PLF-123      # pretty-print a single ticket
task planfile:export PLF-123    # write prompt.md an LLM can eat verbatim
task planfile:sync-todo         # mirror planfile ↔ todo.md
task planfile:auto-loop         # dry-run the full test → ticket → fix loop
```

## Anti-patterns we forbid

| ❌ Don't                              | ✅ Do instead                         |
|--------------------------------------|--------------------------------------|
| Paste stack traces without context   | Include git SHA, env, stack names    |
| Open tickets with no acceptance      | List ≥2 executable assertions        |
| Write "fix this" as the description  | Fill all 7 sections of the template  |
| Use project-specific jargon          | Link to the file, the agent will learn |
| Allow tickets to grow open-ended     | Max 1 week in `open`, then demote    |
| Skip the `llm-ready` label           | Label it so agents know the schema   |

## Integration with redsl / rebuild

- `redsl improve` uses `planfile.yaml` as its backlog when invoked on the
  repo; tickets tagged `llm-ready` are picked up automatically.
- `rebuild restore` writes a `restore-report.md` that links back to the
  ticket ID so the agent can update status on success.

Together the three tools form a closed loop:

```
  Prometheus/TestQL  →  planfile (LLM-ready ticket)
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
   redsl improve   rebuild restore   human + IDE-agent
          │              │              │
          └──────────────┴──────────────┘
                         │
                         ▼
              planfile ticket done <ID>
```
